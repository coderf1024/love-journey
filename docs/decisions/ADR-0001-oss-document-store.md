# ADR-0001：OSS 作为多文档数据库

- 状态：已采纳
- 日期：2026-10-25

## 背景

项目没有后端，但需要保存空间、内容、菜单、订单、钱包、恋爱卡，并支持用户端和管理端同时读写。单文件 `config.json` 会越来越大，订单/卡券并发写时容易互相覆盖。

## 决定

- OSS bucket 下的 `love-journey/db/` 作为文档库。
- 空间/内容/菜单/钱包等有界数据各存一份 JSON。
- 订单、卡券每个记录一份文档，外加 `index.json` 读模型。
- 浏览器通过 `js/oss-utils.js` 的 `dbCollection` 访问，`js/store.js` 提供领域函数。
- 没有后端、没有事务、没有锁；通过读写顺序、回滚和索引重建控制一致性。

## 取舍

- 优点：零运维、零构建、数据结构透明，适合一个人 + AI 的小项目。
- 代价：没有事务/并发控制；索引可能过期；AccessKey 在浏览器里，安全边界是“知道站点的人”。
- 不选择：引入 Supabase/Firebase/自建后端，超出当前项目规模。

## 影响

- 任何写入都必须先只读确认，批量迁移先 dry-run。
- 不要随意增加跨文档的第三次写入；阅读 [OSS 数据安全](../runbooks/oss-data.md)。
- 索引丢失时用 `dbCollection.rebuild()`，不要手写索引。
