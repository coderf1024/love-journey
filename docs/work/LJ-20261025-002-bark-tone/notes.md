# LJ-20261025-002-bark-tone · 笔记

## 决策

- 2026-10-25：通知按收件人拆两套口吻，而不是取中间值。大厨侧要「一眼扫完知道干什么」，用户侧要「像男朋友发来的消息」。原因：两类通知的收件场景和目标不同。
- 2026-10-25：不引入条件语法，用 `{noteBlock}` / `{reasonBlock}` 这种自带换行的块变量解决空值悬空标签。
- 2026-10-25：默认模板不使用 `{minutes}`。`nudgeOrder()` 目前计算的是距下单时间，长预约会得到几千分钟，语义不对；后续单开任务修。

## 发现

- `sendBark()` 原来调用 `barkVariables(space, order)` 后再展开 `variables`，导致 `barkVariables` 内部拿不到 `reason`。改为把 `variables` 作为 `extra` 传入，输出等价，且块变量可以基于 `reason` 生成。
- 出餐有两条推送路径：`serveOrder()`（正常流程）和 `setOrderStatus('served')`（兼容路径）。两处都补了配图逻辑。
- 管理端没有 hash 路由，`{adminUrl}` 落在首页「需要你处理」列表，系统通知的跳转够用。

## 遗留风险 / 后续任务

- 线上已保存的旧模板不会自动更新。
- `{minutes}` 语义待修。
- 通知分组仍是硬编码「恋爱空间」，本次未改。
