## 二、美柚数据导出（能不能导、导什么）

### 结论

**能导出，但官方只提供工作上的一条窄路径。** 具体：

- 公开可查的路径：App 内 **「记录 → 分析」→「导出数据」**，生成 **Excel 文件**，内容包含**经期、体重、症状**等信息（第三方教程口径，多源一致但都不是官方文档）。
- 该入口并非「数据管理」入口，更像分析页的一个导出按钮；不同版本位置可能有变化。**需要人实际导出一份确认列名。**
- 另外按《个人信息保护法》第 45 条，用户有权要求个人信息副本，可通过客服申请——但这不是产品功能，不能作为导入体验的一部分。
- 没有开放 API，没有官方 CSV 规范文档。**不能承诺「一键自动同步」**，只能做「上传文件导入」。

### 对我们的做法

1. 她导出一次 Excel → 空间里「导入美柚数据」→ 选文件。
2. 浏览器内解析。兼容 `.xlsx`（SheetJS 自托管懒加载）和 `.csv`。
3. **列映射界面**：自动猜列（表头关键词匹配），猜不中就让她手动指认「哪一列是开始日期 / 结束日期 / 流量 / 症状」。
4. 预览前 5 条 + 总条数 → 确认后按开始日期去重合并 → 写入 `cycle/periods.json`。
5. 只导入我们能用的字段（开始日、结束日、可选的流量/症状），其余列丢弃，不入库。

### 待离线确认（下次拿到真实文件时）

- [ ] 文件是 `.xlsx` 还是 `.csv`，表头是哪几个字。
- [ ] **一天一行还是「一次经期一行」**。这决定解析策略：一天一行需要合并连续天数为一次经期；一次一行直接映射。
- [ ] 日期格式（`2026/01/25`、`2026-01-25`、Excel 序列号）。
- [ ] 是否包含「预测」列（如果有，不要导入，那是它的推算不是事实）。

导入器应同时兼容两种形态：先按「存在 start/end 列」判断，否则按「一天一行、按流量>0 聚合连续日期」。

## 三、记录与预测（核心，不能输）

### 数据模型（建议）

按 `milestones.json` 心智存有界列表，整份读写：

```jsonc
// love-journey/db/cycle/periods.json
{
  "version": 1,
  "updatedAt": "2026-11-10 16:00:00",
  "items": [
    {
      "id": "pd_20261112",
      "start": "2026-11-12",      // 必填
      "end": "2026-11-16",        // 可空 = 还没结束
      "flow": "light|normal|heavy", // 可空
      "symptoms": ["腹痛", "腰酸"],  // 可空，白名单
      "mood": "low|normal|good",     // 可空
      "source": "app|import",      // 导入来的标 import
      "note": "",
      "createdAt": "…", "updatedAt": "…"
    }
  ]
}
```

```jsonc
// love-journey/db/cycle/settings.json  —— 由管理端写，用户端只读
{
  "enabled": true,
  "homeStripThresholdDays": 7,   // 首页细条：距下次 ≤ N 天 或 经期中 才显示
  "remindEnabled": true,
  "remindDaysBefore": [1, 0],    // 提前 1 天 + 当天
  "remindTime": "09:00",
  "overdueRemindDays": [3, 5, 7, 10], // 过期后第 N 天各推一次，之后停（固定 4 次）
  "showOvulation": true,         // 日历上是否显示排卵期 / 排卵日
  "templates": {                 // 与小灶 Bark 同一套结构
    "before": { "title": "还有 {days} 天", "body": "预计 {range} 开始。\n记得的话点一下记录。", "url": "{url}" },
    "start":  { "title": "预计今天开始", "body": "…", "url": "{url}" }
  },
  "autoTune": true,              // 每次记录后重新回测 27 种组合
  "algorithmOverride": null,     // 管理端可强制指定某组合，null = 自动
  "allowUserImport": true,
  "lastPush": { "date": "2026-11-10", "kind": "before|start|none", "ok": true }
}
```

**为什么整份读写而不是集合**：一次经期就是一条记录，几年也就 60–100 条，远小于 `milestones.json`；索引反而增加写入失败的面。不遵循 `dbCollection`。

### 周期定义

- **周期长度** = 这次 `start` − 上次 `start`（天）。
- 经期长度 = `end` − `start` + 1。
- 未结束的经期（`end` 为空且开始日在最近 10 天内）视为进行中，不参与周期长度样本。
- 异常值：周期 < 15 或 > 60 天标记为异常，默认不进均值，但保留展示（可能是漏记或真的异常）。

### 预测算法 v1（可解释优先）

不做黑盒。步骤：

1. 取最近 `N = 6` 个有效周期长度（不足 3 个不做预测，直接显示「数据不够」）。
2. **加权中位数**，权重按时间衰减 `w_i = 0.85^k`（越近权重越高）→ 得到 `L`。
3. **区间固定 3 天**（人已确认）：以中位数那天的前一天 / 当天 / 后一天为中心窗口；若 P25..P75 本身 ≤ 3 天，直接用真实分位；**若超过 3 天也裁到 3 天**，不因为波动大就放宽。
4. 下一次开始日 = 最近一次 `start` + `L`，区间 = 该日 ±1 天（共 3 天）。
5. 置信度：样本数 + 离散度 → 高 / 中 / 低，三档，文案直白。
6. 展示依据：`基于最近 6 个周期 · 平均 29 天 · 波动 ±2 天 · 区间 11.12–11.14`。
7. **「这次不准」**：记下实际日期，`settings.algorithm` 不变，但该周期进样本；若连续 3 次偏差 > 5 天，提示「你的周期波动较大，这 3 天只是最可能的一段，实际可能提前或推迟」。

### 什么时候触发预测计算

**结论：只有一个触发点——数据变了才重算。除此之外永远读缓存，日期翻篇也不重算。**

#### 唯一触发点：数据变更后

记录开始 / 记录结束 / 补记 / 删除 / 导入完成 / 「这次不准」反馈 —— 任意一次写成功后立即重算，结果写回 `periods.json` 顶部的 `prediction` 缓存。

就这一条。没有别的。

#### 被否掉的两个触发点（人的判断，2026-11-10）

1. **「跨过预测日之后重算」——不做。**
   预测日过了她还没记录，有两种可能：一是预测算错了，二是她确实没记。**从数据上分不出哪种**。这时候重算，等于用「她没记」这个事实去改预测——但没记不等于没来。算出来的还是一个被拖长的周期，越算越偏。
2. **「Workers 每日巡检补算」——不做。**
   Worker 每天 09:00 只做一件事：**读缓存的预测，判断今天要不要推送**。不重算、不写 OSS。这让 Worker 变成一个纯只读的闹钟，出错的面小得多。

#### 预测日过了之后怎么办：不重算，改状态

预测**不改**，但界面上把它标成「已过预计时间」：

- 卡片从「还有 5 天」变成「已过 3 天」，仍然显示原来那个区间，加一句「如果已经来了，记一下为准」。
- 日历上那 3 个虚线圈**保留**，只是变灰（不是消失，也不是移到新位置）。
- 她记录之后，触发唯一的重算，下一次预测自然更新。
- 她一直不记录，就一直显示「已过 N 天」——这本身就是准确的信息。

**为什么这是对的**：预测的价值是「当时这么说」，不是「现在永远对」。把那一次的预测原样留在那儿，才能事后回测「它到底准不准」。如果每次过期就重算，回测对标的是一个一直在动的目标，等于没法验证。

#### 缓存字段

```jsonc
// periods.json 顶部
"prediction": {
  "asOf": "2026-11-07",            // 生成日期（本地时区）
  "center": "2026-11-13",          // 中心日
  "range": ["2026-11-12", "2026-11-14"], // 固定 3 天
  "cycleLength": 29,               // 用的 L
  "sampleSize": 6,                 // 参与中心点计算的周期数
  "confidence": "mid",             // high | mid | low
  "algorithm": { "center": "wmedian", "lambda": 0.85, "window": 6 },
  "backtest": { "hit": 9, "total": 12, "mae": 1.6 },  // 回测摘要
  "dataVersion": "2026-11-07 09:00:02"  // 生成时 periods.updatedAt 的值
}
```

`dataVersion` 的作用收窄了：不是「定时纠错」，而是**读到不一致就说明有人绕过 store 改了数据**（比如手动改 OSS）。这时页面先按旧缓存显示，并保留 `pendingRecompute: true`，等她下次真正记录时一起重算——不在读路径上偷偷改数据。

#### Worker 的职责边界

| 做 | 不做 |
|---|---|
| 每天 09:00 读 `periods.json` 和 `settings.json` | 不重算预测 |
| 按缓存的 `prediction.range` + 设置判断今天要不要推 | 不写 `periods.json` |
| 推送 Bark | 不改任何记录 |
| 把推送结果写进 `settings.lastPush` | 不因推送失败而修改预测 |

`lastPush` 写在 `settings.json`，和预测完全分离。Worker 挂掉最多是没推送，不会影响数据。

### 一次预测几个周期

**结论：一次只预测 1 个周期（下一次），只给 3 天；不预测第 2、第 3、第 4 次。**

理由：

1. **误差会累积。** 每次都叠加大约 ±1.5 天的不确定性，预测第 3 次时区间已经很宽；要维持 3 天窗口就得假装精确，那是骗人。
2. **远期预测没有决策价值。** 她只需要知道「这一次大概什么时候、要不要准备」；三个月后的事问了也不会因此改变行为。
3. **和「不能输」的判断一致。** 美柚会给你一整年的日期表，看起来很全能；我们只给一次，但这次是回测过的、带依据的。

界面上怎么体现「只一次」：

- 日历上**只有一段虚线**（下一个预测窗口），不是每个月都画。
- 预测视图只展示「距离下次」，不出现「下下次」。
- **过期后的补录提醒不是第二个预测**：预测本身不动、不重算；只在过期第 3 / 5 / 7 / 10 天（从区间末日算起）各推一次 Bark，提醒她补录，之后永久停止。固定 4 次，既不会每小时骚扰，也不会无限期拖着。一旦她在任意一天记录，后续未发的提醒全部取消。

  以 11.12–11.14 的预测为例，若一直不记：11.17 / 11.19 / 11.21 / 11.24 各推一次，11.24 之后不再提。

### 排卵日与排卵期（2026-11-10 人要求对齐美柚）

**结论：默认开启显示，用「推算值」的口径，可以关掉。**（人 2026-11-10 明确：直接开，叫「排卵期」。）

#### 算法

```
排卵日 = 预测的下一次经期开始日 − 14 天
排卵期 = 排卵日 − 5 天 … 排卵日 + 1 天（共 7 天）
```

即经典日历法（黄体期固定 14 天）。因为我们的「下一次开始日」本身是 3 天区间，这里的排卵日也**不写单日**，界面上标「推算的排卵日 · 参考值」，点开显示依据和排卵期区间。

#### 三个必须说清楚的点

1. **它是推的，不是测的。** 真正的排卵受睡眠、压力、疾病影响会移动，基础体温和 LH 试纸才测得出来。我们不采集这些数据，就不该装作能知道。
2. **它比经期预测更不可靠。** 经期预测的误差是 ±1 天级别，排卵日是在这个误差之上又叠了「黄体期固定 14 天」的假设，实际偏差可能到 4–5 天。
3. **不能用来自行判断避孕或备孕。** 这是产品底线，界面上必须写一句。写「安全期」三个字是不负责任的。

#### 明确不做

- **不显示受孕概率数字。** 没有任何本地模型能算准，写出来只是装精确。
- **不叫「安全期」。** 叫「排卵期」，语义是「这段时间更可能排卵」，不是「其他时间安全」。
- **不给「最好/最差受孕日」分级。** 那是营销话术。
- **不因为排卵日和她实际感受不符就调整。** 没有反馈入口，因为没有可对照的真值。

#### 视觉

- 排卵期：青色（`--route` / `#2f9b98`）半透明色带，**和经期的粉色明确区分**。
- 排卵日：同一个青色描环，力压色带。
- 日历图例里两项分开写：`排卵期` / `排卵日`。
- 设置项 `showOvulation` 默认 `true`；点排卵日当天可「不再显示」，写进本地偏好。

#### 和「不预测第二次」的关系

排卵日是**基于同一个预测**推出来的，不构成第二个预测——它没有往后跳到下下个周期，只是在当前这个周期里标出一个位置。这一点和「只预测一次」不冲突。

### 边界：什么时候不做预测

| 情况 | 行为 |
|---|---|
| 有效周期 < 3 条 | 不预测，显示「记满 3 次就能预测」 |
| 最近一次开始日距今 > 90 天 | 不预测，显示「数据太久没更新」，请她补录 |
| 最近 3 个周期里有 2 个被标「异常」（<15 或 >60 天） | 仍然给 3 天窗口，但置信度直接标「低」，并提示周期波动大 |
| 正在经期中 | 仍展示下一次预测（不是这次），但日历上不画虚线圈，避免和实心圆混淆 |

### 3 天窗口的直接后果（必须接受）

- 窗口收窄 → 回测命中率一定下降，尤其周期不规律时（原型里「过去 12 次准了 5 次」就是这个示例）。
- 命中率下降不是 bug，是诚实定价：3 天窗口能装下的大部分是规律周期。**这个数字要如实展示，不用更宽的窗口把它做漂亮。**
- 周期不规律的应对不是放宽窗口，而是**提前量**：提醒提前 3 天，按最早可能日备东西（原型「这种时候更适合」卡）。

为什么用加权中位数而不是均值：均值会被一次异常周期（生病、漏记）带偏；中位数对离群点稳健。为什么加时间衰减：周期会随季节/年龄/生活状态漂移。

### 预测是固定算法还是 AI（2026-11-10 追加）

**结论：固定算法族 + 用她自己的历史回测选参数。不上 AI。**

三个理由：

1. **AI 解不了这个问题的瓶颈。** 一个人的周期一年也就 12–13 条记录，导入美柚后大概 40–100 条。这个数据量能支撑的是 3–5 个参数，喂不进任何模型。真正限制精度的是生理波动，不是算法容量。
2. **AI 会让我们变成自己批评的对象。** 我们打美柚的第一条就是「黑盒预测，不给依据」。换成模型预测，同样给不出「为什么是这 3 天」。
3. **架构不允许。** 没有后端，模型要么跑在浏览器里（体积/性能都不划算），要么调外部 API（密钥进公开 bundle + 按次计费 + 断网失效）。为了一个 6 个数就能算的问题付这个代价不值。

#### 算法族（可枚举，全部可解释）

只有 3 个自由度，一共 27 种组合：

| 维度 | 候选 | 默认 |
|---|---|---|
| 中心估计 | 加权中位数 / 加权均值 / `0.7 × 中位数 + 0.3 × 上一次周期` | 加权中位数 |
| 时间衰减 λ | 0.7 / 0.85 / 1.0 | 0.85 |
| 样本窗口 N | 3 / 6 / 12 | 6 |

- 加权中位数：对一次异常周期（生病、漏记、旅行）稳健，均值会被拉偏。
- 时间衰减：周期会随季节、作息、体重、年龄漂移，越近的越相关。
- 「中位数 + 上一次」混合：捕捉周期长度的短期自相关（上个月偏长，这个月往往也偏长，但会向她的均值回归）。对有些人提升明显，对有些人反而变差——所以交给回测决定，而不是拍脑袋。

#### 参数怎么选：走查式回测（walk-forward）

对每个历史周期 i（i ≥ 4），只用 i 之前的数据预测 i，记录实际偏差。27 种组合各跑一遍，选平均绝对误差最小的那个。

- 计算量：27 × 40 条 ≈ 1000 次运算，浏览器里一次性完成，毫秒级。
- **切换门槛**：只有比默认组合平均误差低至少 0.5 天、且回测样本 ≥ 8 次时才切换，避免把噪声当规律（过拟合）。
- **可解释**：界面可以老实写「我们试了 27 种算法，在你的数据上这一种误差最小（1.1 天）」。这句话本身就是差异化，美柚给不出。

这不是机器学习，是**用回测做参数选择**——和机器学习最大的区别是：全部候选都是人能读懂的公式，不存在「模型觉得」。

#### 历史数据多有没有帮助：分三件事看

| 用途 | 有帮助吗 | 说明 |
|---|---|---|
| 预测的中心点（哪三天） | **6 条之后收益递减** | 更早的周期和现在的生活状态可能已经不同。给 5 年前的数据加权，反而拉低精度。所以窗口默认 6，最多 12 |
| 波动幅度（区间和置信度） | **越多越好**，最多到 24 条 | 波动是慢变量，样本越多估得越准。样本少时 MAD 很吵，置信度会虚高 |
| 自检的可信度（准不准） | **越多越好** | 没有历史就没法回测。这也是**导入美柚数据真正的价值**：不是「数据多所以更准」，而是**第一天就能开始校准和度量** |

所以答案不是「越多越好」也不是「越多越没用」，而是：**中心点只用近期的，波动可以用全部的，自检靠总量。**

#### 明确不做的事

- 不做排卵日 / 安全期 / 受孕概率推算。那是另一套模型（基础体温、宫颈黏液、LH 试纸），精度要求高得多，算错代价也大。预测「哪天开始」和预测「哪天排卵」不是同一件事，后者一期不碰。
- 不做 AI 生成式建议（「这几天你可能会累」之类）。听起来贴心，实际是编的。
- 不因为命中率难看就换更宽的窗口。窗口是产品决定（3 天），算法只负责把中心点放准。

### 自检（信任来源）

回测：对每个历史周期 i ≥ 4，用 i 之前的数据预测 i，记录实际落点是否在区间内、偏差几天。展示「过去 12 次预测：9 次落在区间内（75%），平均偏差 1.6 天」。

**这是美柚永远做不到的事**——它不告诉你它准不准。也是我们「不能输」的唯一可靠证明方式。

### 必输防线（显性列出，避免后续被功能膨胀破坏）

- 无广告位、无内容流、无「推荐」。
- 记录入口在首页第一屏，一键完成。
- 预测永远给区间 + 依据，不给假精确。
- 打开就写在本地，网络失败不阻塞。

## 三之二、日历视图（2026-11-10 人要求补充）

### 为什么要有

列表回答「上次什么时候」，日历回答「它到底有没有规律」。同一份数据，两种问题；看连续两次之间的**间距**，日历比数字直观得多。

### 结构

生理期页三个视图，用一个分段控件切换：**日历（默认）/ 预测 / 记录**。

- 月历网格，周一开头（和中国习惯一致）。
- 已记录经期：实心圆（`--stamp`）。
- 预测（3 天）：虚线圈，不填充 —— 一眼分清「发生过」和「猜的」。
- 今天：底部小黑点。
- **导入数据：右上角金色小点**，不隐藏来源。
- 点击任意一天 → 底部弹出当天详情，只给三个动作：这天开始的 / 这天是经期中的一天 / 从记录里去掉。
- 日历本身**只读**，不直接在格子上涂抹（触摸精度不够，容易记错）。

### 数据上的影响

- 不需要新字段。日历完全由 `periods[].start/end` 推导。
- 「这天是经期中的一天」会落到「合并前后相邻记录」的逻辑：若该日期紧邻已有一条记录，则扩展它的 `start` 或 `end`；若独立，则新建一条单日记录（`start === end`）。
- 导入的记录带 `source: "import"`，日历据此画金色小点。

## 三之三、用户端 / 管理端分工（2026-11-10 人要求）

**原则：用户端只做「记录」和「看」；凡是配置都在管理端。** 这样她的界面里没有一个开关，不会因为配错而错过记录；也符合现有分工（用户端管生活，管理端管系统）。

| 能力 | 用户端 | 管理端 |
|---|---|---|
| 记录经期（开始/结束/补记/删除单条） | ✅ | ❌ 只读，不能替她记 |
| 日历 / 预测 / 自检回测 | ✅ | ❌ 看不到逐日明细 |
| 从美柚导入 | ✅ 发起（文件在她手机上） | 可看导入条数结果 |
| 首页细条出现阈值 | ❌ | ✅ 默认 7 天 |
| 提醒总开关 / 时间 / 提前量 / 延后频率 | ❌ | ✅ |
| 提醒文案模板 | ❌ | ✅ 与小灶同一套编辑器 |
| 算法自动重选开关 / 强制指定 | ❌ | ✅ |
| 清空全部记录 | ❌ | ✅ 需输入「清空」二次确认 |

**边界**：大厨能改配置，但**不能替她记录、不能看逐日明细**——健康数据的写权限只在她手里。管理端只显示条数、上次推送状态这类聚合信息。

实现落点：`admin.html` 的「系统」加一个「生理期」卡片（与菜单 / 岁月留痕 / 更新公告 / 空间资料并列）；用户端 `index.html` 的「空间 → 生理期」子页。

## 四、定时提醒方案（GitHub Action 已否掉）

### 需求

每天固定时间检查一次「今天是否该提醒」，到点发 Bark。**一天一次，UTC+8 早上。** 容忍 ±10 分钟延迟；不能容忍连续几天静默失败。

### 候选对比

| 方案 | 免费 | 可靠性 | 落地成本 | 关键限制 |
|---|---|---|---|---|
| GitHub Actions cron | ✅ | ❌ 高负载时延迟可达 5–20 分钟，可能丢队列；**仓库 60 天无活动自动停用** | 低（已有） | 人已否掉；`schedule` 只在默认分支生效，最短 5 分钟间隔 |
| **Cloudflare Workers Cron** | ✅ 每账号 5 个 Cron Trigger | ✅ 以 Cloudflare 的 cron 基础设施为准，**没有仓库不活跃就停用**的问题 | 中：需要 `wrangler` 部署一个几十行的 Worker，另建 Key | 免费版每次触发 **CPU 10ms**；每次跑只是「读 OSS JSON + 算日期 + POST 一次 Bark」，10ms 够用但要注意别做重活 |
| iOS 快捷指令「个人自动化」 | ✅ | ⚠️ 半可靠：**需要设备在、解锁、快捷指令 App 不被杀**；iOS 的「时间触发」自动化在部分版本需要手动确认 | 低（手机侧配置） | 不是一个可以签入仓库的方案；换手机就断 |
| Vercel Hobby Cron | ✅ | ⚠️ Hobby 只支持**每天一次**、精度 **±59 分钟**，官方明确「无法保证准时」 | 中：需要新项目 | 精度太差，9:00 可能 9:59 才发 |
| 阿里云函数计算 + 定时触发器 | ✅ 新用户每月 100 万次调用 | ✅ 商用级 | 中高：要开通 FC、配 RAM 角色、写配置 | 和 OSS 同账号，能走内网；但引入了第二家云的控制台 |
| cron-job.org | ✅ 任务数不限，最小 1 分钟 | ⚠️ 官方明确「不保证准时」；连续失败 25 次会被停用 | 低（纯 HTTP 打点） | 它只能发 HTTP 请求，**不能读 OSS 算日期**——除非我们提供一个无需鉴权、能自行算出结果的端点（等于又要一个 Worker） |
| 自建 Bark 服务端 | ✅ | ✅ | 高 | 需要一台常年在线的机器（树莓派/NAS）。如果家里有 NAS，这是最稳的 |

### 推荐

**Cloudflare Workers Cron**，理由：

1. 它解决的是 GitHub Action 的两个真实痛点——**不因仓库不活跃停用**、**不因共享 runner 排队而漂移**；Cloudflare 的 cron 在边缘调度，是按账号配额而不是公共队列。
2. 免费额度够：一天 1 次，一年 365 次，远低于限制；10ms CPU 对「算个日期 + 一次 fetch」是够的（Bark 请求是 I/O，不吃 CPU）。
3. 和现有架构同构：Worker 只读 OSS 上的 `cycle/periods.json`（匿名可读，和浏览器同一条读路径）+ POST Bark，不写 OSS，**不引入新的数据写入口**。
4. 一个 Worker 文件 ≈ 60 行，`wrangler.toml` 一个文件，能签入仓库（`scripts/cycle-reminder-worker/`），不违反「不新增构建工具链」——它不参与站点构建。

**但有一个前提必须先确认**：`wrangler` 部署需要人拥有 Cloudflare 账号并授权。如果不想引入 Cloudflare，退路是**阿里云函数计算**（同账号能访问 OSS，商用级），或者家里有 NAS 就自建 Bark + 一个 cron。

### 兜底设计（不管选哪个）

- Worker/函数**只做判定，不存状态**：判定逻辑放在 `js/cycle.js`（浏览器和 Worker 共用一份源码，Worker 里 `import` 同一段纯函数）。
- **幂等**：推送前读 `settings.lastPush.date`，同一天已推过就跳过；推送后写回。写回是唯一一次写。
- **失败可见**：推送失败时写 `settings.lastPush.ok = false`，用户下次打开页面看到「上次提醒没发出去」，而不是静默。
- **页面内兜底**：每次打开首页都本地判定一次「今天该提醒但没推」→ 页内横幅提示。这样即使定时器挂了，她也能看到，只是晚了。
